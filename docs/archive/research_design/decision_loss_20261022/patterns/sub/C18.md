# C18 — Shared Interface Bridging Planning and Control
_parent: **Recast Everything Into One Shared Format** (`unify_into_shared_format`)_ · secondary: Re-engineer the Interface, Keep the Backbone · n=14 (oral 1, spotlight 1, poster 9, reject 3)

## Tactical pattern

The shared move is to choose one standardized representation that sits between high-level reasoning and low-level execution, and to make the reasoning model emit exactly that representation so either a downstream executor or the same model can act on it. The interface takes one of a few recurring forms: a shared function-call action vocabulary that pools trajectories from many environments; a discretized codebook of physically feasible action tokens added to the model's vocabulary; structured executable program nodes carrying constraints and preferences that a conventional planner consumes; compact, executor-independent mid-level guidance (entity coordinates, relations, traces) lifted by a simple downstream module; a latent plan embedding passed to a fast controller; or rollouts of future states in the task's own native representation, with actions implicit in transitions. Training is typically staged — low-level grounding or next-state generation first, then planning or reasoning — and is often followed by a reward computed on the interface itself (progress parsed from consecutive states, trajectory agreement with the goal, cross-form consistency, a length penalty that decides when to reason). The load-bearing claim is that a single well-chosen interface lets heterogeneous data be pooled, lets one model plan and act without an external planner or proprietary reasoner, and lets the plan transfer across executors or platforms.

## Step-by-Step

1. Identify the representation gap between what the reasoner naturally produces and what execution needs, and justify why a shared interface is the right fix. Name what is lost or fragmented today: incompatible action formats across environments, text that loses spatial structure, platform-specific skills, or separately generated plan parts that disagree. Papers that cannot show why the chosen interface beats the obvious alternative (separate heads, plain text output, mixed representations) are read as engineering consolidation.
2. Design the interface to be executor-independent and validity-constrained. Make it a closed vocabulary or schema whose every emitted element is executable or parseable — feasible-action tokens, a pluggable function-call set, program nodes with explicit constraints, mid-level guidance a simple module can lift, or native state rollouts a rule-based interpreter can parse into actions. Compare the interface design (codebook size, tokenization, node schema) against alternatives; a weakly justified tokenization or action-space choice is a standing reviewer concern.
3. Convert or synthesize training data into the interface at scale, and audit its quality. Pool heterogeneous trajectories, generate diverse environments with a planner as demonstrator, explore an environment goal-free before proposing grounded tasks, or augment steps with generated rationales — then report how the generated rationales, demonstrations or verifiers were checked. Unquantified quality of model-generated data, the same model serving as executor and verifier, and dependence on a proprietary generator while claiming independence from proprietary systems are recurring objections.
4. Train in stages that separate grounding from planning, then reward the interface output directly where possible. Teach low-level grounding or next-state generation first, add planning or reasoning second, and if using a policy-gradient stage, compute reward on the interface (parsed progress, trajectory agreement, cross-form consistency, reasoning-length penalty). Ablate each claimed design — unified action space, multi-environment pooling, rationale augmentation, two-stage versus single-stage, reinforcement versus supervised-only — because unablated design claims and reinforcement gains that are not disentangled from the architecture were decisive in rejections and in weak posters.
5. Evaluate against task-specific state-of-the-art and in the deployment loop, and scope claims to what was tested. Include specialized prior methods rather than only zero-shot general models, run closed-loop or online evaluation where execution matters, give a failure analysis, and measure the latency and cost of the added interface and downstream modules. Synthetic single-simulator evaluation with weak transfer evidence, unsupported deployment framings (e.g. on-device without measurements), and simple tasks that need little high-level reasoning cap the contribution.

## Differentiation within parent

- vs **Recast Inputs Into Native Instruction Format** (C09): C09 unifies the input side — heterogeneous signals, tasks or settings are rendered or converted into the single format the base model already consumes, and the payoff is instruction-tuning data for understanding or prediction. C18 unifies the output side toward action — it defines the representation the model must emit so that planning connects to an executor or controller, and its payoff is acting and transfer across platforms or environments, frequently with a reward computed on that emitted interface.

## When to pick this one

Pick this when a reasoning model must drive execution across environments, platforms or output forms whose native interfaces are incompatible, AND you can define a closed, parseable representation that a downstream executor (or a rule-based interpreter) can consume and check. If execution is a single fixed platform with abundant native demonstrations, or the interface cannot be validated mechanically, a unified interface adds pipeline cost without a defensible gain.

## Tactical failure mode

The dominant failure is consolidation without insight: pooling existing data into one action format and fine-tuning a stronger backbone, with the claimed design elements (unified action space, rationale augmentation, staged training) never ablated, so reviewers see a data-engineering report rather than a method. A second shape is evaluation that does not match the interface's promise — no comparison to task-specific state-of-the-art, open-loop or synthetic-only testing, simple tasks needing no high-level reasoning, and deployment claims without cost measurements. A third is hidden dependence: the interface works only because external modules (planners, grasp proposals, depth estimators, search-based progress oracles) or proprietary generators carry the difficult part, which is unacknowledged or unmeasured. Self-check: does an ablation show the shared interface itself (not more data or a bigger backbone) causes the gain; is the system evaluated in the loop against specialized methods; and is the contribution of external modules and generated data quantified?

## Examples
### Accepted lessons
- Using rollouts of future states in the task's own native representation as the plan — with actions recovered by a rule-based interpreter parsing consecutive states and rewarded by a progress estimator — can open a reasoning paradigm that does not pass through text, even when validated only on simple discrete environments.
- Using the planner's own stepwise plan as queries that select task-relevant features for a low-level policy links high-level planning to control, and a new structured planning-annotated dataset can carry the contribution despite modest architectural novelty.
- Emitting compact, executor-independent mid-level guidance (entity coordinates and relations) instead of raw low-level outputs sidesteps scarce, target-specific data and enables zero-shot transfer, provided closed-loop results answer the open-loop objection.
- A pluggable shared action vocabulary plus staged grounding-then-planning training succeeds when ablations show the training stages, rationale augmentation and cross-platform pooling each contribute.
- Adding a feasible-action codebook to the vocabulary and a reasoning-length penalty in the reward lets one model learn when to reason, though the tokenization choice must be compared against alternatives.
- Exploring an environment goal-free before proposing tasks grounds synthetic task generation in observed states, making tasks feasible and verifiable — but the verifier must be validated against human judgment.

### Reject lessons
- Consolidating existing datasets into one action interface and training a stronger backbone, without ablating the unified action space, rationale augmentation or two-stage training, is read as limited novelty.
- A submission that is simultaneously a task, a dataset and a method, without justifying the new evaluation against existing ones or comparing to state-of-the-art methods, is judged incoherent.
- Assembling known data-mixing, supervised and verifiable-reward ingredients at a smaller scale, with an unmeasured deployment claim and no artifact release, reads as an engineering synthesis.
